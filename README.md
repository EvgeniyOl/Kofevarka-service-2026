# Kofevarka Service

Сайт мастерской по ремонту кофемашин и магазина кофе: **React + Vite + MobX + TypeScript**,
маршрутизация на `react-router`, стили на CSS Modules, линт ESLint + Prettier, pre-commit хук.

Два направления бизнеса:

- **Ремонт** — бытовые и профессиональные кофемашины, кофемолки и техника для кофеен,
  обслуживание по договору и выезд мастера.
- **Продажа** — кофемашины и кофемолки с гарантией, зерно от обжарщиков, расходники и аксессуары.

Своей обжарки у мастерской нет: кофе закупается у поставщиков, а весь сервис построен вокруг
ремонта и подбора техники.

## База данных

База — обычный PostgreSQL, приложение общается с ним через `pg` и переменную
`DATABASE_URL`. Никакой привязки к конкретному провайдеру нет: Neon, свой
сервер, Docker или managed-база у российского хостера подключаются одинаково —
меняется только строка подключения.

Схему (`users` и `site_requests`) приложение создаёт само при первом запросе
к API, отдельная команда миграций не нужна.

### Локально: Docker

В проекте есть `docker-compose.yml` с готовым PostgreSQL:

```bash
npm run db:up        # поднять базу
```

Затем создайте `.env.local` (образец — `.env.example`):

```
DATABASE_URL=postgresql://kofevarka:kofevarka@localhost:5433/kofevarka
SESSION_SECRET=любая-случайная-строка-от-16-символов
```

Секрет удобно сгенерировать так:

```bash
node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"
```

Дальше `npm run dev` — и регистрация работает. Первый зарегистрированный
пользователь становится администратором.

Порт снаружи — **5433**, а не стандартный 5432: на многих машинах 5432 уже
занят локальным Postgres. Внутри контейнера порт всегда 5432. Данные лежат
в томе `kofevarka-pgdata`, поэтому переживают пересоздание контейнера;
`npm run db:reset` стирает их вместе с томом.

Чтобы поменять пароль или версию Postgres, правьте `docker-compose.yml`.

### На сервере

Тот же `docker-compose.yml` подходит и для VPS: скопируйте его на сервер,
поменяйте пароль и либо не публикуйте порт наружу (если приложение крутится
рядом, они увидят друг друга во внутренней сети Docker), либо открывайте
только с ограничением по IP. Не забудьте про резервные копии — их Docker
не делает.

### Перенос данных

Выгрузка и загрузка — стандартными средствами Postgres:

```bash
docker compose exec db pg_dump -U kofevarka kofevarka > backup.sql
docker compose exec -T db psql -U kofevarka kofevarka < backup.sql
```

## Публикация

Сайт — статика плюс функции API: фронтенд собирается в `dist`, а серверная часть
лежит в `api/` и на Vercel превращается в serverless-функции.

### Vercel (основной способ)

1. Зайдите на [vercel.com](https://vercel.com) и войдите через GitHub.
2. **Add New → Project** и выберите репозиторий `Kofevarka-service-2026`.
   Если проекта нет в списке — нажмите **Adjust GitHub App Permissions**
   и выдайте Vercel доступ к репозиторию.
3. Подключите базу одним из способов:
   - **Storage → Create Database → Neon** — Vercel сам добавит `DATABASE_URL`;
   - или задайте `DATABASE_URL` вручную, если база своя (она должна быть
     доступна из интернета и требовать SSL).
4. Добавьте секрет сессий: **Settings → Environment Variables** →
   `SESSION_SECRET`, значение сгенерируйте командой
   `node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"`.
5. Нажмите **Deploy**.

**Важно:** переменные окружения применяются только к новому деплою. Если вы
добавили их после сборки, сделайте ещё один деплой (Deployments → ⋯ → Redeploy),
иначе функции продолжат работать со старыми значениями.

Папку сборки и команду Vercel определяет сам (`npm run build`, `dist`).
Дальше каждый пуш в `main` публикуется автоматически.

Роутинг обслуживает `vercel.json`: адреса, кроме `/api/*`, отдаются через
`index.html`, поэтому прямые ссылки на `/repair` и `/admin` работают,
а запросы к API уходят в функции. Базовый путь на Vercel — корень домена,
это учитывается в `vite.config.ts` по переменной `VERCEL`.

Таблицы создаются сами при первом запросе к API (см. `api/_lib/db.ts`),
отдельная команда миграций не нужна.

### GitHub Pages (запасной способ)

Workflow `.github/workflows/deploy-pages.yml` собирает и выкладывает сайт
при пуше в `main`. Включить: **Settings → Pages → Source: GitHub Actions**.

Важно: на GitHub Pages нет серверной части, поэтому **авторизация и заявки
там не работают** — страницы входа и админки будут отвечать ошибкой.
Pages годится только как витрина без кабинета.

## Авторизация и заявки

Две роли: **клиент** и **администратор**.

**Администратор в проекте один** — им становится тот, кто зарегистрировался
первым. Все следующие регистрации получают роль клиента, и роль потом не
меняется: ручки для смены роли нет вовсе, поэтому выдать себе права нельзя
даже случайно. Если однажды понадобится второй админ, роль придётся поменять
в базе вручную — в проекте нет интерфейса для этого.

| Метод и путь              | Доступ | Что делает                              |
| ------------------------- | ------ | --------------------------------------- |
| `POST /api/auth/register` | всем   | регистрация, сразу выдаёт cookie сессии |
| `POST /api/auth/login`    | всем   | вход по почте и паролю                  |
| `POST /api/auth/logout`   | всем   | выход: стирает cookie                   |
| `GET  /api/auth/me`       | всем   | кто вошёл (или `null`)                  |
| `POST /api/requests`      | всем   | заявка с формы на странице контактов    |
| `GET  /api/requests`      | админ  | список заявок                           |
| `GET  /api/users`         | админ  | список пользователей с ролями           |

Как устроено:

- **Пароли** — `scrypt` со случайной солью (`api/_lib/password.ts`).
  В базе лежит строка вида `scrypt$<соль>$<хеш>`, сам пароль не хранится.
- **Сессия** — подписанный HMAC-SHA256 токен в httpOnly-cookie на 30 дней
  (`api/_lib/session.ts`). Из браузерного скрипта его не прочитать,
  подделать без `SESSION_SECRET` нельзя.
- **Права** проверяет сервер в каждой ручке (`requireUser`, `requireAdmin`
  в `api/_lib/http.ts`). Ограничения в интерфейсе (`RequireAuth`) — только
  удобство, они не заменяют серверную проверку.
- **Админка** (`/admin`) показывает заявки с формы и список пользователей
  с их ролями. Роль — просто подпись: администратор один, и менять роль
  из интерфейса нечем.

### Проверки

Три уровня — от быстрого к полному. Первые два не требуют базы:

```bash
npm run check:crypto  # хеши паролей и подписи сессий: подделать сессию нельзя
npm run check:api     # ответы API: валидация, коды ошибок, закрытые ручки
npm run check:auth    # вся авторизация: регистрация, роли, права, заявки
```

`check:api` и `check:auth` требуют запущенного `npm run dev` с подключённой базой.
Скрипты лежат в `scripts/`.

`check-auth.mjs` проверяет то, что видно только на живой базе: первый
пользователь становится админом, второму достаётся роль клиента, клиенту
закрыты списки заявок и пользователей, админ не может снять роль с себя,
заявка с формы доходит до базы.

Два правила, о которых стоит помнить:

- проверка «первый становится админом» проходит **только на пустой таблице
  пользователей**. Если аккаунты уже есть, скрипт предупредит об этом и часть
  проверок упадёт — это ожидаемо, а не поломка;
- скрипт **убирает за собой**: удаляет созданные им аккаунты и заявки,
  настоящие данные не трогает.

Полный цикл на чистой базе:

```bash
npm run db:wipe      # очистить таблицы
npm run check:auth   # все проверки пройдут
```

Посмотреть содержимое базы — `npm run db:status`: покажет пользователей
с ролями и заявки.

Адрес — в подпапке с именем репозитория (`evgeniyol.github.io/Kofevarka-service-2026/`),
поэтому для Pages в `vite.config.ts` задан `GITHUB_PAGES_BASE`.
Прямые ссылки на разделы работают за счёт копии `index.html` в `404.html`.

### Локальная проверка сборки

```bash
npm run build -- --base=/   # сборка как для корня домена (Vercel)
npx serve -s dist -l 4180   # статический сервер: http://localhost:4180
```

Флаг `--base=/` нужен, если собираете без переменных Vercel: обычная сборка
рассчитана на подпапку GitHub Pages.

## Разделы, страницы и сторы

У каждого раздела свой компонент страницы и свой стор. Ни корзины, ни витрины
нет: сайт информационный, заказы принимаем по телефону и заявкой.
Всё связывается в `RootStore` (`src/stores/index.ts`).

| Маршрут         | Страница                 | Стор                | Что умеет                                                        |
| --------------- | ------------------------ | ------------------- | ---------------------------------------------------------------- |
| `/`             | `pages/HomePage`         | `HomeStore`         | герой про ремонт и кофе, подборка товаров, порядок работ, отзывы |
| `/repair`       | `pages/RepairPage`       | `RepairStore`       | направления ремонта, этапы, цены, гарантия, FAQ                  |
| `/subscription` | `pages/SubscriptionPage` | `SubscriptionStore` | конструктор плана, расчёт цены, скидки и даты следующей доставки |
| `/about`        | `pages/AboutPage`        | `AboutStore`        | история по годам, принципы, команда                              |
| `/delivery`     | `pages/DeliveryPage`     | `DeliveryStore`     | условия доставки по Омску, подписка, FAQ-аккордеон               |
| `/contacts`     | `pages/ContactsPage`     | `ContactsStore`     | каналы связи, форма заявки, карта Яндекса                        |
| `/login`        | `pages/AuthPage`         | `AuthStore`         | вход в кабинет                                                   |
| `/register`     | `pages/AuthPage`         | `AuthStore`         | регистрация                                                      |
| `/admin`        | `pages/AdminPage`        | `AuthStore`         | заявки и пользователи, только для роли «администратор»           |
| `*`             | `pages/NotFoundPage`     | —                   | 404                                                              |

Вход, регистрация и админка в меню не выводятся: для них есть кнопки в шапке,
а доступ к админке закрывает `RequireAuth` (см. `src/components/RequireAuth.tsx`).

Точка входа — `src/app/router.tsx` (маршруты), каркас с шапкой —
`src/app/Layout.tsx`, справочник путей для меню — `src/app/routes.ts`.

## Дизайн: на чём основан

Перед версткой разобрали, как устроены популярные магазины кофе. Ориентиры:
Blue Bottle, Stumptown, Intelligentsia, Counter Culture, La Colombe, Peet’s,
Nespresso, Lavazza, Illy, Trade Coffee. Из живых примеров — 1790 Coffee
(нарративные «сцены» вместо плоских пакетов), Couplet Coffee (бегущая строка и
неоновые блоки), CONA (рисованные иллюстрации), Damn Fine Coffee Bar (контрастный
чёрный с акцентом).

Что взяли из разбора рынка ([CommerceRank, 2026](https://www.commercerank.ai/guides/themes/best-coffee-themes)):

- **история происхождения и обжарки поставщика** вместо абстрактных описаний;
- **выбор помола и объёма** прямо в карточке;
- **цена за 100 г** рядом с ценой за пакет — честное сравнение 250 г / 500 г / 1 кг;
- **подписка** как основной сценарий повторной покупки;
- **brew-гайды** (рецепты под способ заваривания) — контент, который возвращает клиента;
- **тёплая тёмная палитра**: эспрессо-база, крем, карамельный акцент.

Для сервисного направления добавили то, что спрашивают до звонка: срок диагностики,
ориентиры по цене, гарантию на работы и понятный порядок ремонта.

Отдельно учли главную проблему категории: у кофейных магазинов средний PageSpeed 55 —
их тормозят тяжёлые hero-видео и фото. Поэтому основной визуал сделан на CSS и SVG:
«сцены» карточек — градиенты, чашка — инлайновый SVG с анимацией пара. Фотографии
появились позже и только там, где нужны: герой главной и две карточки в подборке
(источники и лицензии — в `public/photos/CREDITS.md`).

Анимации: появление блоков через `IntersectionObserver` (`Reveal`), набегающие цифры,
пар над чашкой, hover-подъёмы карточек, искры в сцене кузнеца.
Всё уважает системную настройку `prefers-reduced-motion`.

## Как работать с состоянием

1. Состояние раздела живёт в его сторе (`src/stores`), а не в компоненте.
   Локальный `useState` допустим только для чисто интерфейсных вещей вроде
   открытого мобильного меню.
2. Новый раздел — новый стор-класс, подключённый в `RootStore`.
3. Компонент оборачивается в `observer(...)` и получает сторы через `useStore()`:

```tsx
import { useStore } from '../stores/context'

const { home } = useStore()
```

4. Изменять состояние можно только методами (action) стора — так MobX корректно
   пересчитает computed-значения (суммы, скидки, прогресс) и перерисует компоненты.
5. В тестах удобно подставить свой набор сторов: `<StoreProvider store={mockStore}>`.

## Как работать со стилями

Все компонентные стили — только CSS Modules:

```tsx
import styles from './App.module.css'

export function Page() {
  return <main className={styles.page}>…</main>
}
```

Правила:

1. Файл стилей лежит рядом с компонентом и называется `<Компонент>.module.css`.
2. Классы объявляются без БЭМ-разделителей (`-`, `__`) — `camelCase` или одно слово.
3. Глобальным остаётся единственный файл `src/index.css` (сброс, токены, keyframes).
4. Общие примитивы (кнопки, карточки, поля, сетки) живут в `src/styles/ui.module.css` —
   это тоже модуль, просто один на проект.
5. Динамические классы собираются через `cx(...)` из `src/utils/cx.ts`.

  `eslint-config-prettier` (гасит правила, конфликтующие с Prettier).
- Правила намеренно без проверки типов. Для `no-floating-promises` и подобных нужно
  перейти на `tseslint.configs.recommendedTypeChecked` + `projectService: true`.
- Fast Refresh требует, чтобы файл с компонентом экспортировал только компоненты —
  поэтому хук `useStore` живёт в `stores/context.ts`, а провайдер в `StoreProvider.tsx`.

## Pre-commit

`.husky/pre-commit` (активируется на `npm install` через `prepare`) выполняет:

1. `npx --no-install lint-staged` — по файлам из индекса: `eslint --fix` и
   `prettier --write` для кода, `prettier --write` для стилей, разметки и JSON
   (кроме `package-lock.json`);
2. `npm run typecheck` — типы по всему проекту.

Обойти хук для одного коммита: `git commit --no-verify`.

## TypeScript

- `strict` плюс `noUnusedLocals`, `noUnusedParameters`, `noImplicitOverride`.
- `verbatimModuleSyntax`: типы импортируются только как типы.
- Версия 6.0.3 — самая новая из поддерживаемых `typescript-eslint`
  (`>=4.8.4 <6.1.0`). В TS 7 нет классического JS API, на котором держится линтер:
  [issue #12720](https://github.com/typescript-eslint/typescript-eslint/issues/12720).
